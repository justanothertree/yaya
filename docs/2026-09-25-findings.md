# Four things the tests found, and what to decide about each

Written 25 Sept 2026, while adding the first test suite this repository has had.
Nothing here has been changed — each one is a decision about feel, balance or
somebody else's data, and none of them is mine to make alone. Each has a test
that asserts the behaviour **as it is**, so the day you decide, that test is
what turns red.

Ordered by how much they can cost.

---

## 1 · The gallery can lose work when storage fills

**Where** `src/draw/gallery.ts`, `write()`
**Pinned by** `src/draw/stores.test.ts` — "when storage is full it keeps going,
but the work is only in memory"

`write` catches the quota error and carries on — _"storage full or blocked, it
stays for this visit"_ — so a drawing is in memory, absent from disk, and gone
on the next reload. Nothing is said to anybody.

Measured, written the way this store writes it (unpacked):

| a drawing of        | on disk | × 120, the item cap |
| ------------------- | ------- | ------------------- |
| 60 strokes × 20 pts | 19.4 KB | 2.3 MB              |
| 200 strokes × 40    | 118 KB  | **13.8 MB**         |
| 600 strokes × 60    | 515 KB  | 60 MB               |

A typical `localStorage` quota is **5 MB**. A few dozen detailed drawings is
enough to start silently dropping saves.

The maps store beside it carries **both** a byte ceiling and a packed palette
for exactly this reason, and says so in its own comments. The gallery has
neither.

**Three separable decisions**

1. **Pack it**, as `maps.ts` does. Measured at **1.75×** smaller. Backward
   compatible in both directions — `readDrawing` already takes both forms, and
   nine consumers all go through the module's API rather than the key, so none
   of them notices. Cheap, safe, and **not sufficient on its own**: 120 detailed
   drawings is still 7.9 MB packed.
2. **Give it a byte budget**, as maps has. Then the cap is honest, and somebody
   hits a wall they can understand instead of losing work.
3. **Say something when a save does not land.** Today the failure is silent,
   which is the part that turns a limit into a loss.

**My recommendation:** 1 and 3 together. Packing is nearly free and buys real
headroom; telling somebody is what stops the limit being a trap. A byte budget
is the bigger conversation because it means deciding what happens to the 121st
drawing.

## 2 · A diagonal is about 1.3× faster than walking straight

**Where** `src/park/walk.ts`, `stepWalker`
**Pinned by** `src/park/walk.test.ts` — "holding two directions is currently
about 1.3x faster than one"

Measured in screen-heights a second, over three seconds at 240 frames:

| holding  | speed      |
| -------- | ---------- |
| one key  | 0.3392     |
| two keys | **0.4387** |

`stepWalker` plainly means to avoid this. It normalises the steer the moment
`len > 1`, which has no other purpose — and in a file where every deliberate
choice carries a paragraph, that block carries none, which reads as the
standard idiom rather than a decision. But the normalisation only reaches the
**acceleration**; the cap handed to `pull` stays the full `top` on each axis, so
both axes ramp up gently and then arrive at full speed anyway. A diagonal is
slower to get going and then faster, which is not a shape anybody designs.

**The obvious fix overshoots.** Scaling the cap by the wish as well was tried
and measured: it lands the diagonal at **0.914×** straight, not 1.0. `SQUASH`
deliberately makes vertical 0.82 of horizontal, so capping both axes at 0.707
gives `hypot(1, 0.82) × 0.707`.

So _"normalise the steer"_ and _"a diagonal is as fast as walking across"_ stop
being the same instruction the moment the two axes are not equal.

**Two answers, and it is a feel question**

- **Equal on screen** — normalise in screen space, so a diagonal covers the same
  ground per second as walking across. Costs a little more arithmetic.
- **Equal in steer space** — the one-liner, landing at 0.914×. Simpler, and
  slightly _slower_ diagonally than straight, which some top-down games prefer.

**My recommendation:** equal on screen. But how fast you cross the park is the
most-felt number in the game and two directions are held most of the time, so
this wants playing rather than reasoning about.

## 3 · Every boss fissure is a wall

**Where** `src/park/cast.ts`, the `wave` branch of `patchesOf`
**Pinned by** `src/park/cast.test.ts` — "a boss-sized one is not crossable, only
jumpable"

A fissure is five circles spaced along the aim. The spacing is a fixed
`WAVE_GAP` of 1.15 pet-heights — deliberately, so the pattern stays on screen
whatever size the creature is. The **radius scales with the creature**.

Two radii pass 1.15 at exactly **scale 1.25**:

| scale | two radii | floor between steps |
| ----- | --------- | ------------------- |
| 1.0   | 0.920     | 0.230               |
| 1.2   | 1.104     | 0.046               |
| 1.25  | 1.150     | **0.000**           |
| 2.5   | 2.300     | merged              |

And the boss scale band is **2.05 to 3.05**. So this is not "large bosses" — it
is **every** boss. The "cross it" half of what the room tells you about a
fissure has only ever been true for one thrown by a player.

It stays answerable: `CAST.wave.lift` is 0.08, well under `HOP.under` at 0.35,
so it can always be jumped. The move loses one of its two answers, not both.

**Options**

- **Leave it.** A boss fissure is a wall you jump. That is a coherent move, just
  not the one described.
- **Scale the spacing too**, and accept the pattern reaching further — the note
  on `WAVE_GAP` records why that was rejected: at 2.5 the last step landed
  fourteen heights out, half of it off screen.
- **Shrink the radius as the scale grows**, so the gaps survive. Keeps both
  answers and the on-screen footprint.

**My recommendation:** the third, or fix the sentence. What is wrong today is
that the game says "cross it or jump it" and means "jump it".

## 4 · The pounce rate is tuned to a sample of thirteen

**Where** `src/park/temper.ts`, `pounces`
**Pinned by** `src/park/temper.test.ts` — "a pounce is something you actually
see, for every boss"

The note on `pounces` records the rate being set against `charge` landing
between **0.12 and 0.34**, observed across the thirteen drawings on one machine,
inside a band that allows **0 to 0.95**. That fix was right — the previous
setting gave a leap every fifteen seconds, reported as _"i cant notice any
leap"_.

But a horned, four-legged creature in the test zoo comes out at **charge 0.82**
and pounces **every 2.3 beats**. Legal, and outside anything the tuning was
fitted to.

This is the third time this file has had a dial set against the range a formula
_could_ produce rather than the one it _does_ — its own comments record the size
dial and the first cast dial both ending up pinned. The difference here is the
opposite: the observed range was too **narrow**, not too wide.

**Options**

- **Leave it.** Nobody has drawn a 0.82 creature yet, as far as anybody knows.
- **Cap the rate** rather than the input, so the keenest creature pounces at
  most every N beats whatever its charge.
- **Re-fit against the band**, accepting that a sample of thirteen cannot tell
  you the shape of the distribution.

**My recommendation:** cap the rate. It is one `Math.min`, it cannot be
mis-fitted to a sample, and it bounds the thing that actually matters — how
often somebody is being leapt at.

## What is pinned, and what that means

Every finding above has a test that asserts the **current** behaviour, with a
comment saying it is a finding rather than an endorsement. That was deliberate:
a test that quietly encodes a bug as correct is worse than no test, so each one
says which it is and what would have to change.

The tests are `npm run test` — 338 of them, under a second, on pre-push and in
CI.
