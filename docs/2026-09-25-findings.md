# Four things the tests found, and what happened to each

Written 25 Sept 2026, while adding the first test suite this repository has
had. **All four are now closed** — the last two after Evan chose between the
options below.

Two of them turned out to be understated. Worth reading for that alone: in both
cases the first write-up had done the arithmetic the same way the code did, and
so agreed with it.

---

## 1 · The gallery can lose work — ✅ APPLIED, and it was worse than this

**Where** `src/draw/gallery.ts`
**Pinned by** `src/draw/stores.test.ts`

The finding as first written: `write` catches a quota error and carries on, so
a drawing is in memory, absent from disk, and gone on the next reload with
nothing said. Measured unpacked, 120 detailed drawings is 13.8MB against a
typical 5MB quota.

**That was true, and it was not the problem.** Two things were wrong underneath
it.

**The store is not local.** Its own comment said _"local for now, like the song
library"_, and that stopped being true the day `library/cloud.ts` arrived. A
signed-in member's pictures are rows in `member_library` — 400 items, 20MB —
and this store is the copy the app reads. So the numbers above are a **cache**
budget, not the size of anybody's gallery. Reading them as the latter is how
the next one got missed.

**And the cache evicted, which is a delete.** `write` ended with
`slice(0, MAX_ITEMS)`, so keeping a 121st picture dropped the oldest without a
word. `watchLibrary` compares `localRows()` against the previous snapshot and
sends `library_drop` for every slot that has gone — because while it is
watching, "gone from here" can only mean somebody deleted it. That reasoning is
right, and its own comment explains why a cold sync cannot make the same call.
An eviction is indistinguishable from a deletion, so **the browser tidying up
reached the account and took the real copy with it.** Keeping your 121st
picture deleted your first, everywhere.

The same slice was in every store that syncs — songs (200), minions (40), saved
looks — and in the maps store, which does not sync at all and so holds the
**only** copy of a map.

**Done, in `fix(stores): a cache that makes room is a cache that deletes`:**
nothing is dropped to make room in any of the five. A keep that will not fit is
refused and says which of three walls it hit. Replacing a name you already have
is always allowed, because it takes no new room. The gallery also gained the
byte budget it was missing — 200KB a picture, 2MB for all of them, its share of
an origin it splits with the songs, the minions, the maps and the looks.

**On putting it in Cloudflare R2**, which was the preference: it does not help,
and §5 of `CLAUDE.md` already says why — R2 earns its place when real media
arrives, not for stroke lists, and _"one home per thing"_. The vault is already
four times the browser's, on the account. What was broken was not the amount of
room; it was the cache deleting the vault when it ran out.

## 2 · A diagonal is 1.3× faster than walking straight — ✅ APPLIED

**Where** `src/park/walk.ts`, `stepWalker`

Measured in screen-heights a second, over three seconds at 240 frames: one key
0.3392, two keys **0.4387**.

`stepWalker` plainly meant to avoid this — it normalises the steer the moment
`len > 1`, which has no other purpose. But normalising the wish is only half
the answer: it reached the **acceleration**, while the speed **cap** stayed the
full `top` on each axis. So both axes ramped up gently and then arrived at full
speed anyway. A diagonal was slower to get going and then faster, which is not
a shape anybody designs.

**Chosen: equal on screen.** The cap is the wish too, which lands on the
ellipse `SQUASH` already describes:

| holding      | before | after      |
| ------------ | ------ | ---------- |
| across       | 0.3392 | **0.3392** |
| up and down  | 0.2781 | **0.2781** |
| two together | 0.4387 | **0.3102** |

Both straight lines are untouched to four decimal places. Only the diagonal
moves, and it lands between them at 0.914 of across.

**The other reading was not taken.** "Every direction is the same speed on
screen" is one line from here, and it would make walking north 22% _faster_
than it is today — retiring a choice that has its own note above `SQUASH` and
was itself a fix for walking through quicksand. That is a lot of collateral for
a bug about diagonals. Say the word if the park should feel that way instead.

**And it bleeds into the cap rather than snapping to it.** Turning a full-speed
run into a diagonal drops that axis's cap 29% in one frame; a hard clamp spends
it instantly, measured at 29.3% of the creature's speed gone in a single frame.
`pull` walks down at the drag rate — 2.85% a frame, arriving in 43ms.

## 3 · Every boss fissure is a wall — ✅ APPLIED, and every fissure was

**Where** `src/park/cast.ts`, the `wave` branch of `patchesOf`

The finding as first written: the spacing is a fixed 1.15 pet-heights and the
radius scales with the creature, so two radii pass the spacing at scale 1.25 —
and the boss band is 2.05 to 3.05, so it is not "large bosses", it is every
boss.

**Also true, also not the problem.** A creature has a width. `inPatch` expands
every patch by the target's own footprint — `footSpan`, which along the aim is
width × 0.4, and an ordinary creature is half a pet-height wide — so crossing
needs **0.4** of floor, not a number above zero. The old spacing left 0.23.

Swept with `inPatch` itself rather than by doing the sum again:

| scale       | floor between edges | somewhere to stand? |
| ----------- | ------------------- | ------------------- |
| 0.4         | 0.782h              | yes                 |
| **1**       | 0.230h              | **no**              |
| 1.25 and up | 0.000h or less      | no                  |

So **a player's own fissure was a wall too**, and had been all along. The note
calling 0.23 _"the standing room the whole move is built around"_ had done the
sum in circle edges, and the first version of the test asked the same question
the code asked — `gap > r + r` — which is why it agreed.

**Chosen: keep the gaps.** Evan: _"circles on the floor give no blocking depth
so it would just feel bad to be stuck unless we add more visual tells."_

The spacing is now derived from the radius — two radii plus a floor wide enough
for a creature — and the **step count** pays for it, so the pattern cannot
reach further than the field can show. A bigger creature tears the ground in
fewer, fatter bites instead of joining them into a line.

| scale | steps | radius | floor      | far edge          |
| ----- | ----- | ------ | ---------- | ----------------- |
| 0.4   | 5     | 0.184h | **0.500h** | 4.49h             |
| 1     | 4     | 0.460h | **0.500h** | 5.82h _(was 6.2)_ |
| 2.05  | 2     | 0.943h | **0.500h** | 4.89h             |
| 3.05  | 2     | 1.403h | **0.500h** | 6.71h _(was 8.0)_ |

"cross it or jump it" is true again, at every size, for the first time.

**Still open: the visual tell.** The mechanical half is done — you are no
longer stuck. Whether a flat circle on the floor _reads_ as something that
blocks you is the other half, and that is a rendering job rather than a number.

## 4 · The pounce rate is tuned to a sample of thirteen — ✅ APPLIED

**Where** `src/park/temper.ts`, `pounces`

The rate was set against `charge` landing between 0.12 and 0.34, observed
across thirteen drawings on one machine, inside a band that allows 0 to 0.95. A
horned four-legged creature in the test zoo comes out at 0.82 and pounces every
2.3 beats.

**Done: the rate is capped.** `POUNCE_MOST` is 0.25 — one leap every four
beats, which is the number the function's own note already named as the
keenest. So the ceiling is the design rather than something new, and every
charge up to 0.378 sits below it: no creature anybody has drawn changes at all.
What it bounds is the part of the band nothing was ever tested against.

A cap on the RATE rather than on the input, because a cap cannot be mis-fitted
to a sample — re-fitting the slope would have been the third time a dial in
that file was set against the range a formula happened to produce that week.

## What this cost, and the one lesson worth keeping

Two of these four were understated, in the same way, for the same reason: the
write-up measured the thing using the arithmetic the code used. `gap > r + r`
is the fissure's own sum. "120 items" is the gallery's own limit. Neither
question had the third term in it — the creature that has to fit through the
gap, and the sync that reads a disappearance as a delete.

`CLAUDE.md` §2 already says _"measure through a path that shares no arithmetic
with the thing being measured"_, and it is written there about a conversion
factor. It is not only about factors. **A test that asks the same question as
the code will get the same answer, including when that answer is wrong.**

The tests are `npm run test` — 379 of them, under two seconds, on pre-push and
in CI. Every fix here was proved by putting the bug back and watching the tests
go red: the old cap turns three red, the fixed spacing seven, the five slices
five.
