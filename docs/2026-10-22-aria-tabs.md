# The six tab strips get the other half of their contract

**2026-10-22.** No migration, no SQL — this is a front-end pass, recorded here because the
reasoning is the part worth keeping.

## The defect

```
grep -rn 'tablist\|tabpanel\|aria-controls' --include=*.tsx src
```

Six `role="tablist"` strips. Zero `role="tabpanel"`. Zero `aria-controls`.

That is worse than six plain buttons, and the reason is specific rather than pedantic. Declaring
the role makes a screen reader announce "tab, 3 of 6, selected" and offer the reader a move it
cannot make, because nothing on the page says which element holds the answer. A row of plain
`<button>`s announces nothing and promises nothing; a half-declared tablist describes a behaviour
that is not there. It is the same argument the chronicle strip's own comment already made about
the arrow keys, pointed at the structure instead.

`ddec9dd` had fixed the keyboard half for chronicle only — roving tabindex, arrow keys, wrapping,
selecting as it moves. The structural half was left deliberately for one pass across all six,
because doing one leaves the app inconsistent. This is that pass, and it turned out the other
five had no keyboard half either.

## What each strip needed, and why they are not all the same shape

Four attributes: an `id` and an `aria-controls` on each tab, `role="tabpanel"` and an
`aria-labelledby` on the panel. The interesting part is where the panel _is_, which differs:

| Strip              | Panel                   | Shape                                                       |
| ------------------ | ----------------------- | ----------------------------------------------------------- |
| `EvanCook` About   | `.about-a`              | one element, reused                                         |
| `ProfileBlocks`    | `.profile-blocks-grid`  | one element, reused, **only a panel when the strip exists** |
| `Chronicle`        | a new `<div>`           | a contiguous run of ~600 lines, wrapped                     |
| `AppearanceDialog` | each `.appearance-body` | six elements, one mounted at a time                         |
| `manager` (snake)  | each `.snake-side-body` | three elements, one mounted at a time                       |
| `AudioVisualizer`  | a new `.viz-panel`      | sixteen blocks, interleaved per tab, wrapped                |

**Where one element already exists, the role goes on it** rather than on a wrapper around it.
Twice that was not a style preference but the only safe option: `.appearance-body` is the flex
item that owns the dialog's scroll and its deliberately fixed frame, and `.snake-side-body` is
both the aside's scroller and the thing `.snake-stage-side:not([data-open]) .snake-side-body`
shuts below 860px. A parent around either would have taken the scroller's job and left the other
rule pointing at the wrong element. Only one body is ever mounted, so one stable id on whichever
is mounted is correct, and the label follows the open tab. In `AppearanceDialog` that id is
passed into `LooksTab` as a `PanelAttrs` prop, since its root is an `.appearance-body` like the
other five.

**`ProfileBlocks` is the half that points the other way.** One section is the overwhelming
majority of pages and draws no tabs at all, so the role is conditional on `sections.length > 1`.
A `tabpanel` with no tab anywhere on the page is the same broken contract, mirrored.

**`AudioVisualizer` could not avoid a wrapper**, and could not be made tidy either. Its four
tabs' rows are interleaved in source order rather than gathered per tab — Sound's controls sit
either side of Motion's and Look's — so no tab owns a contiguous element and the ids have to be
unique. One panel around the whole run is the only shape available. Three things inside it belong
to no tab (the party row, the feedback warning, the no-microphone note); they already drew among
the tab content and still do. Gathering each tab's rows together would be tidier and would move
controls on screen, which is a different change from giving the strip a panel.

## Two things the wrappers could have broken, and the measurement that settled it

Wrapping is a structural change, and the honest check is not "it looks fine".

**Chronicle.** `.chron` is a plain block card, so a wrapper's margins should collapse through it.
Rather than reason about that, the live DOM was put back to a run of siblings
(`panel.replaceWith(...panel.childNodes)`), measured, and restored. Wrapped and unwrapped were
**pixel-identical** — every rect, the strip-to-blurb gap, the list-to-`YourCopy` gap, the card
height and the document height — and the restore matched the original.

**The visualiser.** This one would have broken. `.viz-controls` is
`display: flex; flex-direction: column; gap: 0.5rem`, so wrapping sixteen flex items into one
would have deleted every gap between the rows of a tab. `.viz-panel` carries the same column and
the same gap, plus `flex: 0 0 auto` — a single flex item in a fixed-height column is the one
shape flexbox squashes to fit instead of overflowing, a question sixteen items each resisting at
their own content height never had to answer. Same A/B on the Sound tab (5 rows): gaps identical
(9px each), element tops identical, `.viz-controls` `scrollHeight` identical at 698px both ways.
The measured tab heights in that file's comment still hold.

**And the first attempt at that measurement was wrong**, which is worth writing down. The control
chosen was the gap between `.viz-tabs` and `.viz-presets` — supposedly "a `.viz-controls` gap I
did not touch". It read 0, because `.viz-tabs` is `position: sticky` with
`margin: -0.5rem -0.6rem 0`: the one element on the strip whose spacing is special. A control has
to be a thing the bug cannot also affect.

## The keyboard half, now shared

Five strips needed it, so it is `src/ui/tabStrip.ts` rather than five copies, and chronicle's
local `moveTab` now calls it. Its reasoning — that it wraps, that it selects as it moves because
every strip here is a client-side filter, and that it must stop the event or App.tsx's window
listener walks the viewer off the page — moved with it.

Two decisions in it are not obvious:

- **It answers `null` below two tabs**, so a lone tab does not swallow the key. The snake's panel
  is one tab in solo, and a strip with nowhere to move that claimed ArrowRight would take the key
  and then do nothing with it. Measured in the room: ArrowRight on the lone Settings tab goes to
  site navigation, `#games` → `#visualizer`.
- **Left and Right only.** All six strips are horizontal, and a horizontal tablist answering
  ArrowUp would be taking a key the page has a use for.

`tabKeyTarget` is pure and tested from the strip's _shape_, not the function's sum: walking right
`n` times from any start visits every tab exactly once and comes home, left undoes right, Home and
End do not wrap, unclaimed keys return null. Each test was made to fail once by reintroducing the
bug it is for — no left wrap, a lone tab claiming the key, End off by one, ArrowUp answered — and
all four went red. Note that the range sweep _cannot_ catch End-off-by-one, because the modulo
wraps `count` back to 0; the explicit Home/End test is what bites. Two tests, two questions.

## `useId`, not written-in names

Every id is `useId()` plus an index. Three of these components can be on a page twice —
`AudioVisualizer` draws in its own section, a pinned canvas window and a profile block;
`ProfileBlocks` renders a second real grid in the editor — and a written-in name would be two
panels answering to one id with a tab pointing at whichever came first. `ProfileBlocks` has a
second reason: its section names are typed by the member, so a space, a quote or an emoji in one
would be an id that cannot be pointed at. React 19 mints `_r_0_`-style ids, which are
selector-safe. Measured with two strips on one page: `_r_0_` and `_r_1_`, no collision.

## What was verified, and where

A DOM probe per room checking that each tab has an id, each `aria-controls` resolves to a real
element, that element is a `tabpanel`, its `aria-labelledby` resolves to the **selected** tab, and
exactly one tab is at `tabIndex` 0 — plus a sweep for panels no tab controls. **The probe was
perturbed before being believed**: a dangling `aria-controls`, a panel with no `aria-labelledby`,
a label left on the wrong tab, every tab a tab stop, and a missing panel role were each injected
into the live DOM and each reported, and the strip read clean again afterwards.

Driven with **real key events** through the pane, not synthetic ones:

- About — ArrowRight moved selection, focus and the answer shown.
- Chronicle — wrap off the end to Today, End, Home, wrap backwards to Years; the label followed
  every time. Panel boundaries checked by containment: blurb, weight line and goal list inside;
  the strip, timer, rail, intro and `YourCopy` outside.
- Profile sections — ArrowRight changed the grid from 6 blocks to 2.
- Visualiser — ArrowLeft wrapped from Modes to Motion (1 row → 4); **ArrowUp did nothing**, as it
  should.
- Appearance — all six tabs walked and wrapped, with exactly one `.appearance-body` mounted
  throughout, the panel id stable, and the body still the dialog's scroller.
- Snake — one-tab passthrough, and the two-tab lobby strip moving, swapping the body and wrapping.

**The positive control, which is the point of CLAUDE.md §2:** with focus on `document.body`,
ArrowRight still walks the site, `#home` → `#circuit` → `#ratings`, and ArrowLeft comes back. A
guard with no positive control is a guard that might have turned the feature off. The hash never
moved while a tab had focus, in any of the above.

`scripts/mobile-audit.js` at 375 on both wrapped rooms, with content in them rather than empty:
chronicle (5 goals) reported every figure zero; the visualiser with its tray open and four rows
reported `sideways 0, offEdge 0, clipped 0, spills 0, insideOut 0`. `spills` is the rule that
would catch a flex wrapper putting content past its own box, which is the failure `.viz-panel`
could have introduced. The two remaining visualiser findings — a 51×14 slider value and two
icon-only buttons explained by `title` — are pre-existing and untouched here.

Checked in the **production bundle** on `:4173` as well, which is a different program and a fresh
origin: About, the visualiser tabs and the appearance dialog all clean there, with a real
ArrowRight moving an appearance tab and the label following. Chronicle and the profile grid need a
session, so those two were verified only against the dev preview harness.

## What is not done

- **No screen reader was used.** The original note in `docs/2026-10-12-chronicle-design.md` said
  the benefit could not be verified without one, and that is still true. What is verified is that
  the relationships resolve, which is the thing that was missing.
- **No `tabIndex={0}` on the panels.** The APG asks for it only when a panel holds nothing
  focusable, and for the profile grid that is a question about whatever blocks a member put there
  — a runtime fact, not one this pass can settle. The association was the broken contract; this
  is a separate decision.
- **The snake's three-tab lobby state** (`players`/`settings`/`room`) was not reached; it needs a
  live relay room. The two-tab browsing state was, and the wiring is the same code.
- **Firefox and Safari**, as always — the pane is Chromium.
