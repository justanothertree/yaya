# Supabase failures read as answers: an audit (read-only, nothing changed)

Asked for on 27 Nov 2026 after #471. That bug: `hostOfParkRoom` treated a failed owner lookup as
"this park has no owner" and cached it until the relay restarted. The question is where else that
happens.

**Nothing in this document has been changed in code.** It is a list to decide from.

## The bug class

supabase-js 2.107 does not throw on failure. A network error, an HTTP 4xx or 5xx, an RLS refusal, a
timeout or an abort all resolve to `{ data: null, error, status }`. Only `.throwOnError()` throws.
So two shapes are bugs:

- **try-catch-only:** the call is wrapped in `try`/`catch` and never reads `error`. The catch never
  runs, and the failure flows on as `data: null`.
- **data-null-as-answer:** `null`, `[]`, `0` or "no row" is read as a real answer ("nobody owns it",
  "not a member", "no ratings") without first checking `error`.

In `server/`, a raw `fetch()` to Supabase is the same class: a non-2xx response resolves, so a body
parsed without checking `r.ok` is shape two.

"Could a failure be cached?" asks whether the wrong answer outlives the failure, and where it is
kept.

## How it was done

The audit read `server/` and `src/` at `0a64475a`, excluding tests.

- Eight readers each took a group of files, listed every call site and classified it. They traced
  wrappers to see what each one does with `error`.
- A second reader per group tried to refute every flagged site and its cache claim, spot-checked the
  ones called fine, and grepped for sites the first reader missed.
- A coverage critic searched four more ways for calls nobody had listed: other client names, raw
  `fetch` to `/rest/v1`, `/rpc`, `/auth/v1` and `/functions/v1`, and modules importing the client.

**Line numbers are at `0a64475a`.** Main has moved since, so check before editing.

## The numbers

- **492** call sites in `server/` and `src/`, every one classified.
- **119** in the bug class, after the second reader refuted 3 and reclassified 7. By how long the wrong answer lasts:
  - written-to-server: 10
  - server-memory: 1
  - persisted-local: 13
  - memory-until-reload: 3
  - ui-until-remount: 61
  - no: 30
  - n/a: 1
- **35** more read `error` and then return a default (`[]`, 0, "none") as though it were the answer. That is the same mistake with one more line. They are listed separately at the end; 2 of them are written back to the server.

## What to look at first

Ranked by what a failure costs. A blip turns into:

1. **Privacy: a real name shown where somebody chose an alias.**
   - `src/circuit/ui/Chat.tsx:314`: the result of `set_lounge_display_name` is ignored. On a failure the alias is shown locally while every Lounge message after it is stored under the real name, permanently. An alias over 40 characters fails every time.
   - `src/circuit/ui/Chat.tsx:138`: a failed `my_lounge_display_name` read publishes the real name in Lounge presence.
2. **A failed read shown as empty, and the next save writes that empty back over real data.**
   - `src/components/CertainChooser.tsx:163,175`: the owner is told an item is private when friends can see it. One tap then replaces the whole stored list.
   - `src/circuit/supabaseAdapter.ts:320`: saving a rating from the blank editor erases the stored review and icons; Save with no change deletes the rating.
   - `src/circuit/supabaseAdapter.ts:310`: typing into a blank day overwrites that day's entries.
   - `src/circuit/supabaseAdapter.ts:299`: clearing a day's visible numbers can delete a row that has sessions.
   - `src/sections/AccountSettings.tsx:643`: Save names blanks the other nicknames.
   - `src/chronicle/cloud.ts:303`: ± writes 0±1 over a goal window's real count.
   - `src/chronicle/cloud.ts:751`: a sitting moved across midnight leaves its sets behind.
   - `src/finance/portfolio.ts:252`: an admin re-assigning what looks unassigned writes a duplicate allocation.
3. **The relay, for the life of a socket.**
   - `server/ws-server.js:2891` (verifyToken) and `:2902` (inGoodStanding): a blip during the one `auth` frame reads as signed out or not in good standing. The client never re-sends `auth` (`src/game/net.ts:93`), so a Snake handle goes uncredited for the round and a park or bout player is refused at 12 s.
   - Latent and fail-open: `:1073` reads a 2xx NULL from `is_suspended` as good standing.
4. **Saved on the device and painted again next visit.**
   - `src/circuit/supabaseAdapter.ts:304-319`: any failed table becomes an empty board, written over the good cached one.
   - `src/App.tsx:931,938,948`: `is_admin`, `my_features` and `my_account` failures are saved as flags. A failed `my_account` opens a paused member's UI back up; the server still refuses them.
   - `src/game/leaderboard.ts:85`: renames a player to an existing `Player1`.
5. **Lost silently.**
   - `src/library/cloud.ts:307` (`library_drop`) and `:143` (`library_put`): a failed drop or edit is counted as sent and never retried, so a deleted item comes back.
   - `src/App.tsx:685`: a profile look that failed to publish is never re-sent.

The other 61 are shown wrong until the view is opened again, and 30 are wrong for that one call only. Those are mostly empty lists standing in for "could not load". They are worth one shared fix rather than 91 separate ones.

**#471's own fix holds:** `server/lib/parkHost.mjs:46` was classified as the reference. Only a 2xx answer is believed, and a failure is retried after 30 s.
